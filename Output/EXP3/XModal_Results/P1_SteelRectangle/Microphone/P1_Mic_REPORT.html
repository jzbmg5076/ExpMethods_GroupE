Coherence — what it meant for this test

What coherence is. For every hit point the analyzer averaged several hammer hits (ensembles). Coherence γ²(f) = |Gxy|² / (Gxx·Gyy) compares the averaged cross-spectrum of hammer force (x) and sensor response (y) with their auto-spectra. It answers: “at this frequency, how much of the measured response is explained linearly by the measured hammer force?” γ² = 1 means every hit gave the same input–output relationship (clean, repeatable, linear); γ² near 0 means the response at that frequency was mostly noise or something not caused by the force.

How to read it here. High coherence (≥0.9) at the resonance peaks is what matters, because that is where the modal fit gets its information. Dips are normal and expected at anti-resonances and at points that sit on a nodal line of a mode (almost no response, so the signal is buried in noise). Broad low-coherence bands across many frequencies usually mean a bad set of hits (double hits, hammer skidding, too-soft/too-hard tip), the plate rattling on its supports, or sensor/cable noise. Coherence only tells you about repeatability of the measurement – not whether the sensor was in a good place, and not whether the fit is right.

Wizard vs hand picks

What the Pole Wizard does. After the green start button, X-Modal fits the FRFs again and again at increasing model order (rows 1–20 of the consistency diagram). A pole that keeps showing up at the same frequency, damping and mode shape as the order rises is a physical mode; poles that move around are mathematical noise. The symbols say how consistent each pole is: blue diamond = frequency, damping and shape vector are stable (“pole & vector”), green triangle = frequency + damping stable, red triangle = frequency only, magenta circle = only its conjugate. The Wizard only accepts columns that build into a black cluster square – i.e. mostly blue diamonds – and averages the cluster.

What a hand pick is. When a real peak has no cluster (only red/green triangles), the Wizard skips it. You can click a single symbol in that column (we used the highest model order, 19) to add that one pole to the list. That is a hand pick.

The practical differences.

  • Frequency – hand-picked and Wizard frequencies are both accurate to within about half a frequency line (±1.95 Hz here) of the independent Python fit; frequency is the easiest thing to get right.
  • Damping – a hand pick is one pole at one model order, not an average of a stable cluster, so its damping is less trustworthy (it is usually the number that moves most from order to order). Treat hand-picked damping as approximate.
  • Why a mode fails the Wizard – the mode is weakly excited or weakly seen by the sensor at most points, it is very close to a stronger mode, it is heavily damped (wide, low peak), or the sensor sits near its nodal line. A hand pick is legitimate only if the peak is clearly visible in the raw FRFs and the resulting animated shape makes physical sense (we also checked it against NX with MAC).

This plate

Three of seven modes needed hand picks – more than any accelerometer set. A microphone hears a mode only as much as the mode pushes air at the mic location, so modes that radiate weakly toward the mic (and the two lowest modes, whose peaks are small in the mic FRFs) never build a fully stable pole-and-vector column. The hand-picked shapes still match NX well (MAC 0.98, 0.99, 0.92).

What Python was used for

  • Reading the raw files. Each lab .mat file is an X-Modal UFCELLS cell array. Python (scipy.io.loadmat) pulled out the FRF (dataset 58, type 4), the coherence (dataset 58, type 6), the frequency spacing, the timestamp and the channel labels – the numbers in the raw-data tables and plots come straight from these files.
  • Fixing the point labels (reciprocity relabel). The Channel Dialog was left at its defaults, so every file said Response = CHAN 2, Reference = CHAN 1. X-Modal cannot build a mode shape from 15 files that all claim to be the same DOF. Because the sensor stayed fixed and the hammer roved, each file is H(sensor, hit j) = H(hit j, sensor) by Maxwell reciprocity, so Python rewrote only the labels to Response = hit point j (+Z), Reference = sensor node (+Z). The data values were not touched (checked to machine precision).
  • Writing the X-Modal input files. Python wrote the Universal File (.unv) datasets 151 (header), 164 (units), 15 (nodes), 82 (tracelines) and 58 (FRFs) in the exact fixed-width format X-Modal accepts, and re-read every file with the pyuff library to confirm node numbers, labels and data.
  • An independent cross-check of the fit. A separate least-squares fit (one pole shared by all hit points in a narrow band around each peak, plus residual terms) gave a second set of frequencies, damping and mode shapes. It is only a check on X-Modal, not a replacement.
  • NX comparison. Python read the NX .op2 result files (pyNastran), took the out-of-plane displacement of the top-surface node nearest each hit point, and computed MAC (Modal Assurance Criterion) between each measured shape and each NX shape.
  • Pictures. All plots in this report (grid maps, raw FRFs, coherence, NX comparisons, hand-vs-Wizard) were drawn with matplotlib. The X-Modal animation videos (.mov) were recorded inside X-Modal; Python/ffmpeg only cut each one into a 3-second looping GIF and picked the frame of largest deflection as the still image.

Python never replaced X-Modal for the modal fit: every frequency and damping value reported as “X-Modal” was read from X-Modal's Group Manager.
